## 1. Введение

### 1.1 Назначение документа

SDD описывает способ реализации RateFlow: компоненты, интерфейсы, алгоритмы и проверяемые системные требования. Разработчик использует документ для реализации, тестировщик — для подготовки проверок, заказчик — для оценки компромиссов. Основа — [SRS](../srs.md); изменения объёма согласованы в [учебной переписке](../correspondence.md).

### 1.2 Область применения

RateFlow показывает официальные ежедневные курсы USD, EUR и RUB к BYN, конвертирует суммы и формирует уведомления внутри приложения. В релизе 0.2 добавлен CSV-экспорт текущего снимка; графики 7/30/90 дней перенесены в 0.3 по CR-02. Аккаунты, синхронизация, банковский обмен, сравнение курсов банков и фоновые push-уведомления отсутствуют. Обновление выполняется при открытии, вручную и каждые 60 минут открытого приложения.

### 1.3 Определения, акронимы и сокращения

| Термин | Определение |
|---|---|
| ADR | Протокол архитектурного решения |
| API | Программный интерфейс |
| Cache | Последний корректный снимок курсов |
| Номинал | Число единиц валюты, к которому относится опубликованный курс |
| Нормализованный курс | Курс одной единицы валюты: rate/scale |
| SDD | Software Design Description |
| SRS | Software Requirements Specification |
| stale | Сохранённые данные с неподтверждённой актуальностью |

## 5. Приложения

### 5.1 Функциональные требования и приоритеты реализации

10 — наивысший приоритет, 20 — высокий, 30 — средний, 40 — низкий, 50 — минимальный. Оценки — базовые человеко-часы опытного разработчика с UI, API и проверками функции. P0 сохраняет исходное предложение, P1 — результат первого раунда, P2 — действующий план после второго. Детали и согласования — [correspondence.md](../correspondence.md).

| ID | Feature | Требования SRS | Приоритет | Оценка, ч | Зависимости |
|---|---|---|---:|---:|---|
| F01 | Official rates & resilient refresh | REQ-FUNC-001, REQ-REL-001 | 10 | 48 | W00 |
| F02 | Currency preferences | REQ-FUNC-002 | 20 | 16 | F01 |
| F03 | Currency converter | REQ-FUNC-003 | 10 | 32 | F01 |
| F04 | Historical charts | REQ-FUNC-004 | 20 | 64 | F01 |
| F05 | Alert rules | REQ-FUNC-005 | 30 | 32 | F02 |
| F06 | Rate change notifications | REQ-FUNC-006 | 30 | 56 | F01, F05 |

Таблица сохраняет первоначальное предложение для сравнения с перепиской. Актуальный состав 0.2 — в §6: графики отложены. W00 — каркас, прототип НБРБ, проверка контракта и схема кеша, 24 ч; W09 — сквозная приёмка качества, поставка и документация, 32 ч. Общие работы обязательны, приоритет 10. Исходная оценка — 304 ч. Проверки отдельных функций уже в их оценках, W09 проверяет интеграцию.

## 7. Динамическое поведение версии 0.3

Дата: 23.11.2026. Этот раздел и V09–V12 проектируют объём [SRS 0.3](../srs.md#lab5-scope). Разделы 1–6 и V01–V08 сохраняют проект 0.2/план P2 как историческую основу. Для 0.3 уточняются доступ, хранение личных данных и возврат графиков; публичная интеграция, десятичные вычисления и CSV сохраняются. Реализация и испытания нового объёма пока не подтверждены.

### 7.1 Состав представлений

| ID | Назначение | Модель | Сценарии |

| V10 | Сквозной поток с альтернативами | Б: активность | Курсы → конвертация → график → вход → правило → событие |

Изображения и механизмы моделей встроены в [view.md](view.md#v09). Термины вынесены в [глоссарий](../docs/glossary.md), общие ограничения — в [дополнительные спецификации](../docs/supplementary-specification.md), полные потоки и постусловия — в [use-cases.md](../docs/use-cases.md).

### 7.2 Логические компоненты и данные

| Компонент | Ответственность в 0.3 |
|---|---|
| Public Rates/History UI | Публичное чтение курсов, даты/номиналы, графики и пустые/ошибочные состояния. |
| ConverterController / ConverterService | Клиентский контроллер формы и сервис сценария; ввод, Decimal-расчёт и показ результата. Имена в Г не навязывают HTTP-размещение. |
| RateProvider | Граница получения публичных данных через backend-адаптер НБРБ и кеш. Не получает пользовательскую сумму. |
| Session / Account module | Проверка подготовленных аккаунтов, сессия и определение владельца. Регистрация и админ-UI не добавляются. |
| RuleService / EventService | Авторизованные операции с правилами/событиями, атомарное сравнение и фиксация обработанной даты. |
| RuleRepository / EventRepository | Постоянное хранение с обязательным ownerId; локальный UI-кеш не определяет права доступа. |

Расширение существующего SQLite-хранилища для учётных записей, правил и событий сохраняет один backend; отдельный PostgreSQL или микросервис из диаграмм не следует. Публичные снимки хранятся отдельно от личных сущностей. В Rule требуются id, ownerId, currency, threshold, enabled и lastProcessedDate. В Event — ownerId, ruleId, даты, валюта, направление, исходный процент и read. Уникальность правила — `(ownerId,currency)`, события — `(ownerId,ruleId,currentEffectiveDate)`. Удалённое правило не используется для новых проверок; готовое событие содержит собственные данные для истории.

### 7.3 Дополнительные системные требования

**SYS-AUTH-001:** сервер проверяет учётные данные и связывает сессию с пользователем; выход/истечение исключают личные операции. Проверка: UC-000 с неверным паролем, отказом сервера, сменой пользователя и истёкшей сессией. Planned.

**SYS-OWNER-001:** каждое чтение/изменение Rule/Event проверяет ownerId из сессии. Идентификатор из тела запроса не является доказательством владения. Проверка: две учётные записи и подмена id для GET/PUT/DELETE. Planned.

**SYS-RULE-001:** изменение правила атомарно и сохраняет диапазон/шаг порога, единственность валюты и отметку обработанной даты. Включение не порождает дубликат. Проверка: UC-004/008/009, повтор запроса, конфликт записи и ошибка сохранения. Planned.

**SYS-EVENT-001:** проверка порога и запись обработанной даты выполняются вместе с созданием события в одной транзакции. Уникальный ключ владельца/правила/даты защищает повторы из двух вкладок. Отключение/удаление, stale и отсутствующий previous исключают новое событие. Лимит — последние 100 событий владельца. Planned.

**SYS-CALC-002:** конвертер переставляет выбранные валюты, оставляет введённую сумму и заново проверяет/считает результат по SYS-CALC-001. Пользовательская сумма не передаётся backend/НБРБ и не записывается в журналы. Planned.

Для 0.3 SYS-AUTH-001/OWNER-001/RULE-001/EVENT-001 заменяют положения SYS-STORE-001, SYS-ALERT-001 и SYS-SYNC-001 о единственном локальном источнике личных данных и локальном ключе revision. Для публичных предпочтений IndexedDB допустим. SYS-HIST-001 теперь проектируется в 0.3, проверка Planned; статус Deferred 0.3 относится к историческому выпуску 0.2. Другие числовые критерии сохраняются.
